# 浏览器

客户端不是浏览器，但 agent 需要一个浏览器。它是 agent 在容器里用的工具，和 git、编译器同一类。目标：登录状态和打开的页面跨机器同步，接管后不用重新登录。纳入 MVP。

## 同步哪些状态

| 层 | 包括 | 是否同步 |
| --- | --- | --- |
| 登录状态 | cookie、localStorage、IndexedDB | 同步。换机器后不用重新登录 |
| 标签页 | 打开了哪些页面、每页的 URL | 同步，在新机器上重新打开这些 URL |
| 页面运行时 | JS 内存、WebSocket 连接、表单里没提交的内容 | 不同步，和"迁移运行中的进程"一样是非目标 |

接管后的效果相当于"同一个浏览器配置，把所有标签页刷新了一遍"。

## 设计

- **运行位置**：每个会话的容器里跑一个无头 Chromium。agent 通过 CDP 控制它，用现成的 Playwright MCP 之类即可，这一层不要求 Rust。
- **导出而不是复制目录**：不直接复制 Chromium 的用户目录。那个目录是带锁的 SQLite 和 LevelDB 文件，运行中很难拷出一致的副本。改为在每个检查点通过 CDP 导出一份状态：cookie、各站点的 storage，加上标签页 URL 列表，打包成一个小文件（通常几 KB 到几 MB）。内容没变（hash 相同）就不传。
- **按凭据对待**：cookie 就是登录凭据。状态文件用池的 DEK 加密，像凭据库一样在节点之间点对点同步；不进工作区，也不进 git 快照。会话日志里只记它的 hash `B`，和 `workspace = T` 写在同一个批次里，同样遵守"先推对象，再推引用它的批次"。M4 之前没有 DEK，用手工配置的池密钥。
- **接管时**：新 driver 启动一个新的 Chromium，导入登录状态，重新打开那些标签页。
- **单写者**：浏览器归 driver 所有，热备只持有状态文件，不运行浏览器。

## 浏览器操作的重做

浏览器里点一下可能就是提交订单、发帖，属于"外部不可核对"。被打断的浏览器调用**不自动重做**，而是告诉 agent："浏览器已恢复、页面已刷新，上一个操作是否完成不确定"，让它先看页面再决定。

## 人工接管登录

客户端可以经 iroh 实时看到容器里浏览器的画面（CDP screencast）并操作它。遇到验证码、两步验证时，你在客户端里亲手登录一次，登录状态随后同步，以后哪台机器接管都不用再登。放在 M5 客户端一步做。

## 风险

- cookie 会过期；有的站点会因为 IP 或设备指纹变化让登录失效。接管后若发现登录失效，提示你在客户端里重新登录。
- 状态文件是敏感数据，移除节点时按凭据泄露处理（见[环境与凭据](04-environment-and-credentials.md)）。
