# 端侧模型服务

> 状态：MVP 之后。MVP 只预留两处：节点名册里的能力字段，和容器里的本地接口地址。

harness 统一管理端侧辅助模型：语音转文字、文字转语音、AI 绘图等。它们不属于某个会话，而是池里的公共服务：哪台机器能跑就放在哪台，所有会话都能调用。

原因在硬件：每台机器能跑的模型不同（例如 pc 有 NVIDIA 显卡，mac 节点是 Linux VM、用不到 Apple GPU）；模型文件动辄几 GB，不适合跟着检查点复制。

## 设计

1. **节点上报能力**：入池时上报硬件（显卡型号、显存）和能跑的模型，写进节点名册。
2. **统一接口**：每个容器里提供一个本地地址，接口仿照 OpenAI 的格式（语音转文字、文字转语音、生成图片各一个）。很多现成工具认这个格式，agent 用什么语言调都行。
3. **harnessd 转发**：容器里的请求先到本机 harnessd，再经 iroh 转给装了该模型的节点。会话跑在 mac 上也能用 pc 的显卡。
4. **推理后端用现成的**：例如 whisper.cpp / sherpa-onnx 做语音转文字，Piper / Kokoro 做语音合成，stable-diffusion.cpp / ComfyUI 画图。这一层不要求 Rust，harnessd 只负责启动、停止和转发。
5. **模型文件按内容寻址**：用 hash 标识，第一次用时从 Hugging Face 下载，或从池里已有该文件的节点点对点拉取（iroh 支持大文件传输）。每个节点只在本地缓存，不进检查点。
6. **显存调度**：消费级显卡一次只放得下一两个模型，请求排队，闲置一段时间自动卸载。

## 和替补的关系

模型调用不改变状态、不涉及外部操作，属于"内部操作"，重做没有代价：

- 装模型的节点掉线，请求换一台有能力的节点重试；没有能接手的，就报错给 agent。
- 生成的图片、音频写进工作区，随快照同步；单个文件超过 50 MB 时跳过，规则照旧。

## 取舍

想用 mac 的 GPU，模型服务必须直接跑在 macOS 上，不能放在 Linux VM 里，这会打破"只支持 Linux"的约定。先只让 Linux 节点提供模型服务，mac 原生的以后再说。
