# 服务模型

项目分两层：**框架**在设备之间同步和调度，**服务**干具体的活。框架不知道服务内部是什么，只看服务声明的契约。本篇定义这份契约，并说明现有和计划中的服务各自落在哪一类。

> MVP 只实现 agent 会话这一个有状态服务。这里的契约是**设计边界**，不是要求 MVP 先写出一个通用插件系统：代码上先保证框架核心不依赖任何具体服务（尤其不依赖 goose），等第二个有状态服务出现时，再把通用接口提炼成 trait。

## 服务契约

每个服务声明以下几项：

| 项 | 内容 |
| --- | --- |
| 名称与实例 | 服务类型名（如 `session`、`llm`、`stt`）；有状态服务可以有多个实例（如每个会话一个） |
| 状态类型 | 见下表，决定框架怎么对待它 |
| 放置约束 | 需要的硬件（显卡、显存、内存）、平台（Linux / macOS）、是否需要容器 |
| 接口 | 对外暴露什么：容器内的本地地址（如 OpenAI 兼容 HTTP）、本机 unix socket，或 iroh 上的协议 |
| 生命周期钩子 | 启动、停止、健康检查；重启策略（连续失败几次后熔断） |
| 调用截止时间 | 每次调用的默认超时；超时、断连都转成结构化错误返回调用方，不让调用方无限等待 |
| 状态钩子（仅有状态服务） | 打检查点、导出快照、从快照还原、追平 |
| 外部副作用分类 | 内部 / 外部可核对 / 外部不可核对，决定替补后的重做规则（见[会话与替补](02-session-and-failover.md)） |

### 三种状态类型

| 状态类型 | 例子 | 框架负责 | 故障时 |
| --- | --- | --- | --- |
| **单写者有状态** | agent 会话、数据库 | 租约与 epoch、检查点、点对点复制到热备 | 热备接管，从检查点恢复 |
| **无状态** | 本地 LLM、语音转文字、文字转语音、绘图 | 按能力放置、按负载路由、显存调度 | 换一台有能力的节点重试 |
| **仅本地缓存** | 模型文件、`/cache` 下的编译缓存 | 不同步；按内容寻址，可从其他节点点对点拉取 | 本地重新下载或重新生成 |

## 框架提供什么

| 能力 | 说明 |
| --- | --- |
| 名册与能力 | 节点列表、在线状态、硬件能力（架构、核数、内存、显卡与显存） |
| 租约与 epoch | 给单写者有状态服务的每个实例发写权限 |
| 点对点复制 | 按 seq 复制服务产生的批次和快照对象，遵守"先推对象，再推引用它的批次" |
| 放置与调度 | 根据放置约束决定服务跑在哪台节点；有状态服务选热备，无状态服务选能力匹配、负载低的节点 |
| 路由 | 服务的调用方不关心服务在哪台机器上：harnessd 在本地暴露接口，请求经 iroh 转给实际运行的节点 |
| 凭据 | 按服务声明注入凭据 |
| 通知 | 服务上报"需要人处理"的事件，框架统一发给客户端 |

## 现有与计划中的服务

| 服务 | 状态类型 | 放置约束 | 接口 | 阶段 |
| --- | --- | --- | --- | --- |
| agent 会话（含工作区、浏览器） | 单写者有状态 | Linux 节点，需要容器运行时 | iroh 上的会话协议（客户端用） | MVP |
| 本地 LLM（如 Qwen 系列 0.8B–4B） | 无状态 | 内存足够即可；小模型可用 CPU | OpenAI 兼容 HTTP | MVP：作为模型提供方的配置项；MVP 后：纳入统一模型服务 |
| 语音转文字、文字转语音、绘图 | 无状态 | 通常需要显卡 | OpenAI 兼容 HTTP | MVP 后，见[端侧模型服务](06-local-models.md) |
| 数据库 | 单写者有状态 | 待定 | 待定 | 待定，见下文 |
| 托管的外部工具（如后台运行、提供 MCP 的游戏引擎编辑器） | 多为无状态，项目文件在工作区里 | 视工具而定（显卡、平台） | MCP | MVP：调用截止时间与自动重启；MVP 后：熔断、自建 fork |

### 数据库：待定

"数据库"可能指两种完全不同的东西，在架构里的位置不同：

- **项目里用的数据库**：agent 开发某个项目时要起一个 Postgres 之类。它属于会话环境的一部分，跟着会话的容器走，数据目录放在工作区或单独的卷里，随会话检查点同步。
- **你自己的数据**：笔记、记忆、向量库等，跨会话、跨设备共享。它是一个独立的单写者有状态服务，有自己的租约、检查点和复制。

两者都需要时，前者先做（它只是会话服务的扩展），后者作为第二个有状态服务，也是提炼通用服务接口的时机。

## 单机时

框架层照常运行，只是仲裁者是内置在 harnessd 里的本地仲裁（见[概览](01-overview.md)的「部署形态」）：

- 单写者有状态服务：租约永远归本机，照常打检查点、崩溃后恢复，只是没有热备。
- 无状态服务：只能放在本机；本机跑不了的服务（比如没有显卡时的绘图）显示为不可用。
- 路由退化成本机调用。
