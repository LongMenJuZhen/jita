# 设计原则

**定位：让 agent 无人值守地、又快又稳地跑长任务的执行环境。**

三条原则各自不新鲜：可恢复的 agent 执行、并行子 agent、通过 MCP 暴露 harness，都已经有人做过。少见的是三条合在一起，并且跑在你自己的设备上、数据不上云。三条互相加强：池子提供并行需要的机器，面向 agent 的接口让一个管理者 agent 能用上并行，可靠性让无人值守的长任务敢放手跑。

设计取舍时按这三条判断；和它们无关的功能，优先级往后放。

## 一、可靠：适应比一般 harness 更多的异常

一般的 harness 默认机器一直在、工具一直响应、人一直在看。我们不这样假设，每一类异常都要有明确的应对：

| 异常 | 应对 | 设计在哪 |
| --- | --- | --- |
| 节点掉线 | 热备在约 30 秒内接管，最多重做一个工具调用 | [会话与替补](02-session-and-failover.md) |
| 进程崩溃 | 从会话日志和检查点恢复，单机也一样 | [会话与替补](02-session-and-failover.md) |
| 外部工具失联或卡住 | 每个工具调用都有截止时间、可取消，超时返回结构化错误，绝不让整个会话卡死；托管的工具自动重启 | 本节下文、[服务模型](10-services.md) |
| 模型不可用（断网、额度用完） | 降级到本地小模型，并提示当前在用降级模型 | [端侧模型服务](06-local-models.md) |
| Cloudflare 不可用或额度耗尽 | 任务继续跑，暂停外部操作和替补，并说明原因 | [会话与替补](02-session-and-failover.md) |
| 人不在 | agent 能接手管理工作，只在必须由人决定时才打扰 | 第三条 |

### 工具托管

外部 MCP 工具失联，是长任务最常见的卡死原因。框架把需要常驻的工具当成[服务](10-services.md)来看管：

- **最基本、MVP 就要做的**：每个工具调用有截止时间；超时、断连都转成 agent 能理解的结构化错误（"工具不可用，原因是……"），而不是无限等待。
- **托管**：常驻的工具进程（例如一个后台的游戏引擎编辑器提供 MCP）按服务契约声明健康检查和重启策略，由框架拉起、监控、失败时重启，连续失败就熔断并告诉 agent。
- **先包装，后 fork**：优先用原版工具加外层包装实现托管；只有原版确实做不到（比如无法无界面启动、无法稳定提供 MCP）时，才考虑维护自己的 fork。例如"harness 启动时自动起一个后台 Godot 提供 MCP"，先尝试原版 Godot 的无界面模式加插件。

## 二、速度：减少模型的等待和往返

大模型的能力不缺，缺的是速度。一个任务的耗时绝大部分花在等模型上，harness 本身很少是瓶颈。所以提速的重点是**减少等模型的次数和时间**：

- **并行**：能拆开的子任务同时跑，见下文。
- **减少往返**：让模型写一段脚本一次做完多件事，而不是逐个调用工具（code mode 的思路）。
- **工具本身要快**：搜索、建索引、跑测试都用最快的实现；常驻服务避免反复冷启动。
- **便宜的子任务交给本地小模型**：摘要、起标题、分类等。

Rust 的价值主要在可靠、单个二进制、启动快、资源占用低，让 harness 自身的开销可以忽略；不要指望它让模型变快。

**衡量**：用两个指标评估提速是否有效——完成一个任务的总耗时，以及模型往返次数。

### 并行与单写者

并行和会话的单写者设计冲突：多个子任务不能同时写同一个会话、同一个工作区。做法是**拆成子会话**：

- 会话之间有父子关系。父会话（通常是一个管理者 agent）创建子会话、布置任务、等待结果、合并。
- 每个子会话是独立的单写者有状态服务实例，有自己的会话日志、工作区（独立的 git 分支或工作树）和租约，可以放在池里不同的节点上跑。
- 合并走 git：子会话在自己的分支上提交，父会话负责合并和解决冲突。
- 池里的机器既是热备也是并行的算力。调度要权衡：机器忙于跑子会话时，谁来当热备。

MVP 只在会话模型里预留父子关系，并行调度放到 MVP 之后。

## 三、面向 agent 的接口（agent native interface）

任务能拆分、能持续，人也很难随时响应。所以 harness 要设计成 agent 也能用：一个 agent 可以接收一份详细的长任务说明，自己拆分、派发、等待、验收，只在必须由人决定时才找人。

### 只有一套操作

GUI、TUI、MCP、命令行**共用同一套操作定义**，都只是它的外壳。操作定义在协议层（`crates/protocol`），例如：

- 创建会话、创建子会话、布置任务、发消息、停止回合；
- 查询会话、节点、检查点、副本状态；
- 批准或拒绝外部操作、交接会话、处理分叉；
- 订阅和等待事件（"等这个子会话结束"、"等需要批准的事件"）。

人能在客户端里做的事，agent 都能通过 MCP 做；反过来，只给 agent 开放的操作也要在客户端里看得见。这件事越早定越便宜，等界面写完再补就很贵。

### agent 当用户时的额外要求

- **能等事件，不靠轮询**：提供订阅和带超时的等待。
- **权限分清**：每个操作标明谁可以做。管理者 agent 不能批准自己或下属 agent 的外部操作，否则"需要你批准"形同虚设；哪些操作必须由人批准要明确列出。
- **返回结构化结果**：给 agent 的是机器可读的数据，给人的是界面，两者来自同一份数据。
- **重复请求不重复执行**：所有会改变状态的操作都带 `requestId`，复用会话日志的去重机制。

## 对 MVP 的取舍

三条原则都会把范围变大。MVP 只放下面几项，其余放到 MVP 之后：

| 进入 MVP | MVP 之后 |
| --- | --- |
| 工具调用的截止时间与结构化超时错误 | 常驻工具的熔断；自建工具 fork |
| 托管工具的基本重启（随服务契约） | 并行调度、子会话放置到不同节点 |
| 统一的操作定义：在协议层定下来，先实现几个核心操作，GUI / TUI / MCP 都从它生成 | 完整的管理者 agent 工作流 |
| 会话模型预留父子关系 | 权限模型的细化 |
